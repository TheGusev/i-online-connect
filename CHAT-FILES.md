# Документы и сохранение фото

## Сделано

- Скрепка рядом с фото в обоих чатах: один файл до 25 МиБ, без сжатия; прогресс, ошибка и повтор с тем же clientTempId.
- PDF, UTF-8 TXT/CSV, DOC/DOCX, XLS/XLSX, PPT/PPTX, ZIP и растровые изображения JPEG/PNG/WebP/GIF/BMP/TIFF/ICO/AVIF/HEIC/HEIF. SVG и другие активные форматы запрещены.
- Расширение и содержимое проверяются сервером; MIME клиента не используется. Office ZIP проверяет каталог, соответствующую главную часть и отсутствие VBA; старые Office — OLE-сигнатуру и поток формата. ZIP не распаковывается. TXT/CSV проверяются как UTF-8 без бинарных управляющих байт/известных префиксов скриптов: отдельной сигнатуры у текста нет. Это не антивирус; Office/архивы только скачиваются.
- Имя очищается от пути, управляющих/направляющих символов и ограничивается 120 символами. На диске UUID, исходное имя только в БД.
- Файлы находятся в `${MEDIA_DIR}-documents`, за пределами всех публичных каталогов. Скачивание требует авторизацию и актуальное участие; отправка — ту же видео-верификацию/блокировки, что фото.
- PDF/изображения выдаются inline для просмотра, остальные attachment; `?download=1` всегда attachment. Правильный Content-Type, UTF-8 Content-Disposition, nosniff, private/no-store и sandbox.
- Карточка с именем/размером/значком/скачиванием; TXT/CSV — текст первых 256 КиБ, PDF — окно и отдельная вкладка, изображения-файлы — просмотр, прочие документы — только скачивание.
- Ответ/реакции/удаление используют прежние действия. Список личных чатов и уведомления о личных сообщениях получают `Файл: <имя>`. Новая система уведомлений сообщества не вводилась.
- «Сохранить» в меню фото и текущем полноэкранном просмотре; «Скачать» в меню файла. На компьютере download, на iPhone Web Share с File, при отсутствии поддержки/ошибке — новая вкладка. Для фото подсказка «Удерживайте картинку и выберите «Сохранить»». Сохраняется одно открытое фото, «Сохранить все» не добавлено.
- Простая трактовка удаления: только **новые kind=file** физически удаляются; прежние фото/голосовые/видео и фото-альбомы сохраняют существующее мягкое удаление. Это исключает изменение ранее согласованного поведения медиа. Запись file-сообщения остаётся, но доступ сразу закрыт обоим; повторное удаление повторяет очистку при прежней ошибке диска.

## Миграция и выкладка

`037_chat_files.sql`: новый enum file, optional поля имени/размера в обеих таблицах, расширенные CHECK с обязательными полями/лимитом для file. Проверка enum через `kind::text` позволяет применить всё одной транзакцией. IF NOT EXISTS и пересоздание именованных CHECK делают повтор безопасным; старые миграции не изменялись.

Применить 037 через `npm run migrate` в server, обновить API и собрать/выложить `dist/static`. Процессу API нужны права создать соседний каталог `${MEDIA_DIR}-documents`; включить его в резервные копии, **не** добавлять публичный alias Nginx. Новых библиотек/ключей/переменных нет. Рабочий сервер не изменялся.

## Проверки и ограничения

- 037 применена и повторно применена транзакционно в отдельной PostgreSQL.
- 9 серверных тестов прошли: запрещённые расширения/подмена/скрипт как текст, точные границы 25 МиБ, OOXML/ZIP, права и неверифицированный аккаунт в обоих чатах, metadata/идемпотентность, заголовки, чтение списка, физическое удаление и 404 после удаления, PDF inline/attachment.
- 15 серверных регрессий сообщений сообществ и реакций прошли (включая сохранение старых медиа при удалении).
- 47 клиентских тестов чатов/scroll-lock прошли, включая 4 новых теста лимита/выбора режима просмотра/скачивания. Новые модули проверены ESLint, серверные типы tsgo чистые, автоматическая клиентская сборка/типы build OK. Серверный tsc и production-сборка отдельно не запускались.
- Chromium 393×852 с реальным временным Fastify и отдельной БД: файл CSV в обоих чатах → карточка → текстовый просмотр → скачивание → содержимое совпадает → перезагрузка показывает тот же файл. Переадресация Playwright опускает бинарную часть multipart; тест восстановил её из того же выбранного CSV перед передачей настоящему API, не подменяя ответы/данные.
- В полном просмотре сохранено настоящее фото; скачанные байты совпадают с оригиналом. Ошибок JavaScript в проверенных сценариях нет.
- Настоящий iPhone Safari/PWA и системное Web Share/«Сохранить в Фото» не проверены; PDF встроенный рендерер iOS, HEIC/AVIF-декодирование на конкретном устройстве, production API/БД/права каталогов не проверены. Нужны устройство и доступ к серверу владельца. В браузере проверен обычный download, логика iPhone — чистыми тестами.
