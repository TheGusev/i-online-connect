# Белый экран в установленном приложении после обновления

## Что реально происходит (проверено по коду)

Файл предполагает, что виноват кэш service worker. Это не так: `public/sw.js` ничего не кэширует — там только push-уведомления, и `skipWaiting()` + `clients.claim()` уже вызываются. Поэтому переписывать стратегии кэша в service worker не нужно, иначе я «исправлю» то, чего нет.

Подтверждённые слабые места:

1. Главная страница отдаётся без запрета кэширования. В инструкции для сервера запрет стоит только на адрес `/index.html`, а установленное приложение открывает `/` — этот ответ веб-вью на iPhone кэширует по своему усмотрению. Старая разметка ссылается на файлы, которых после обновления на сервере уже нет (старые копии удаляются при выкладке), приложение не может загрузить свой код — белый экран.
2. Нет никакой защиты на случай, если код всё же не загрузился: ошибка загрузки модуля нигде не перехватывается, пользователь просто видит пустоту.
3. Баннер «Вышло обновление» появляется только пока приложение открыто и только по опросу файла версии; он не помогает в момент запуска со старой разметкой и не обновляет сам service worker.

## Что сделаю

**Защита от белого экрана в приложении.** Перехватываю ошибки загрузки кусков кода (не загрузился модуль / ошибка сети при подгрузке) и один раз автоматически перезагружаю страницу с обходом кэша. Один раз — чтобы не было циклической перезагрузки: факт попытки запоминаю на время сессии, при повторе показываю понятный экран «Не удалось загрузить обновление» с кнопкой «Обновить». Это же покрывает случай, когда старая разметка ссылается на удалённые файлы.

**Проверка версии при запуске и во время работы.** При старте приложение сверяет свою версию с версией на сервере. Если разметка старая (устройство открыло закэшированную копию) — тихая автоматическая перезагрузка с обновлением service worker. Если приложение уже работает и вышло обновление — прежний неблокирующий баннер, но кнопка сначала обновляет service worker, затем перезагружает. Интервал проверки — 3 минуты (уже есть), плюс проверка при возврате в приложение (уже есть) и при событии online.

**Service worker.** Добавляю только то, чего не хватает: очистку любых кэшей, оставшихся от прошлых версий (на устройствах, где раньше стояла кэширующая версия, мусор мог остаться и продолжает мешать), и сообщение странице о том, что активировалась новая версия. Кэширование не добавляю — офлайн-режим не заказан, а именно он и создаёт этот баг.

**Настройка сервера.** В инструкции по серверу правлю раздачу так, чтобы главная страница и файл версии никогда не кэшировались (запрет и для `/`, и для `/index.html`, и для service worker, и для файла версии), а файлы с хэшем в имени — кэшировались навсегда. Это обязательная часть исправления: без неё устройство продолжит открывать старую копию.

## Полная диагностика (вторая часть просьбы)

Отдельно прогоняю сквозную проверку приложения и правлю найденное:

- открываю каждый экран в браузере через автоматизацию, собираю ошибки в консоли и неудачные запросы: лендинг, вход, онбординг, лента, профиль свой и чужой, чаты и диалог, «Рядом» и создание объявления, пространства, уведомления, настройки, верификация, безопасность, правила, поддержка;
- проверяю мобильный размер экрана 393×626 — ничего не должно налезать и обрезаться;
- проверяю заголовки и описания страниц, сборку статики и типы;
- всё найденное либо исправляю, либо перечисляю в отчёте с причиной, если исправление выходит за рамки этой задачи.

## Техническая часть

- `src/lib/chunk-recovery.ts` (новый): слушатели `error` (capture) и `unhandledrejection`, распознавание `ChunkLoadError` / «Failed to fetch dynamically imported module» / «Importing a module script failed», одноразовый флаг в `sessionStorage`, `location.reload()`; экспорт состояния для показа fallback-экрана.
- `src/hooks/useAppVersion.ts`: сравнение с версией, вшитой в бандл (`import.meta.env.VITE_BUILD_VERSION`, подставляется в `vite.config.static.ts`/`scripts/build-static.mjs` из `APP_VERSION`/git-хэша); при расхождении на первой проверке — `registration.update()` + одноразовый `location.reload()`, в остальных случаях — флаг для баннера; слушатель `online`.
- `src/components/UpdateBanner.tsx`: кнопка вызывает `navigator.serviceWorker.getRegistration()?.update()`, затем `location.reload()`.
- `src/routes/__root.tsx`: подключение `chunk-recovery` в `useEffect`, рендер fallback-экрана при повторном сбое загрузки.
- `public/sw.js`: в `activate` — `caches.keys()` + `caches.delete()` для всех кэшей, `postMessage` контроллируемым клиентам о новой версии.
- `SERVER-SETUP.md` и `DEPLOY.md`: `location = /` и `location = /index.html` → `Cache-Control "no-store"`, `location = /sw.js` и `location = /version.json` → `no-cache`, оставить `immutable` только для `/assets/`.
- Проверки: `bunx tsgo --noEmit`, `bun run build:static`, `bunx vitest run server/tests`, прогон экранов через Playwright на локальном сервере.
- Новых пакетов, переменных окружения и миграций нет.

Реальный прогон на вашем iPhone с уже установленным приложением остаётся за вами: в песочнице нет живого устройства и выложенной новой сборки. После выкладки я скажу, какую последовательность проверить.
