# Админка со скрытым входом + защита от ботов, спама и инъекций

Backend админки (роли, `requireAdmin`, `/api/admin/*`, аудит в `admin_actions`
и `logs/admin-audit.log`) уже готов и протестирован. Этот план добавляет
скрытый вход с TOTP, интерфейс админки и усиление защиты всей платформы.

## 1. Скрытый вход

Путь берётся из `VITE_ADMIN_PATH`, значение по умолчанию — `panel-x7f2k9`
(поменяете в `.env` перед сборкой, логика не меняется).

Чтобы путь оставался настраиваемым, добавляем один универсальный маршрут
`src/routes/$.tsx` (catch-all). Он сравнивает первый сегмент адреса с
`VITE_ADMIN_PATH`: совпало — показывает админку и разводит подразделы по
остатку пути; не совпало — обычная страница «Ничего не найдено». В дереве
маршрутов, навигации, подвале и sitemap путь админки не фигурирует нигде.

- `public/robots.txt`: `Disallow: /panel-x7f2k9` для всех агентов + `noindex`
  в мета-теге самой админки.
- Форма входа — своя, не переиспользует `/auth`: email, пароль, обязательный
  код из 6 цифр. Неверная пара, отсутствие роли `admin` и неверный TOTP дают
  один и тот же ответ «Проверьте данные», без подсказок.
- Отдельная короткая сессия: свой токен на 2 часа, хранится в
  `sessionStorage` (закрыли вкладку — вход заново), без авто-обновления.
  По истечении — экран повторного входа.

### TOTP (Google Authenticator)

- Миграция `007_admin_totp.sql`: `users.totp_secret` (зашифрован),
  `users.totp_confirmed_at`. Additive.
- Шифрование AES-256-GCM ключом из `TOTP_ENCRYPTION_KEY`.
- `npm run grant-admin -- email@example.com` генерирует секрет, печатает
  `otpauth://`-ссылку и ASCII-QR **только в терминал** один раз; повторный
  показ — только через `--regenerate`. Ни секрет, ни ссылка, ни QR не идут
  в логгер и не отдаются ни одним HTTP-эндпоинтом.
- `POST /api/admin/session` проверяет пароль argon2 → роль → код TOTP
  (окно ±1 шаг, защита от повторного использования кода) и только тогда
  выдаёт админ-токен. Любой шестизначный код не принимается.

## 2. Интерфейс админки

Плотная табличная вёрстка на существующих компонентах `src/components/ds`:
боковая навигация + рабочая область с фильтрами. Все изменяющие действия —
через `Modal` с подтверждением.

| Раздел | Содержимое |
| --- | --- |
| Пользователи | Таблица с поиском по email/имени, фильтрами по верификации и блокировке; карточка: профиль, медиа, история входов, сессии, жалобы; кнопки Заблокировать / Разблокировать / Удалить |
| Жалобы | Очередь с фильтром по статусу, детали, решение модератора |
| Верификации | Видео заявки и фото профиля рядом для сравнения, Подтвердить / Отклонить |
| Объявления «Рядом» | Таблица с фильтром по статусу, снятие с публикации и возврат |
| Поддержка | Очередь обращений, статус, поле ответа (уходит письмом) |
| Сообщества | Список с числом участников и событий, удаление |
| Статистика | Графики на `recharts` (уже в проекте): регистрации за 30 дней, активные сессии, матчи / сообщения / объявления |
| Журнал действий | `admin_actions` только для чтения |

## 3. Защита от спама, ботов и инъекций

### Лимиты (Redis)

Хранилище — Redis через `ioredis`, адрес из `REDIS_HOST`, `REDIS_PORT`,
`REDIS_PASSWORD`, `REDIS_DB` (ничего не захардкожено). Пока переменные не
заданы, сервер работает на счётчиках в памяти и пишет предупреждение в лог —
после включения Redis в панели Beget достаточно внести значения в `.env`.

| Маршрут | Лимит | Ключ |
| --- | --- | --- |
| Весь `/api` | 100 / мин | IP или аккаунт |
| `/api/auth/register` | 5 / 10 мин | IP |
| `/api/auth/login` | 10 / 10 мин | IP |
| `/api/confirm/*` | 3 / 10 мин | аккаунт |
| `/api/support` | 5 / час | IP |
| `POST /api/listings` | 10 / день | аккаунт |
| `/api/admin/*` | 30 / мин | IP + аккаунт |
| `POST /api/admin/session` | 5 / 15 мин | IP |

Часть значений сейчас мягче (общий лимит 300/мин, объявления 20/час) —
приведём к указанным.

### Остальное на сервере

- Honeypot-поле в регистрации и создании объявления: заполнено — ответ
  «успех» без записи в базу, без объяснений.
- Капча: Yandex SmartCaptcha на регистрацию и форму поддержки для гостей.
  Ключи в `YANDEX_CAPTCHA_SECRET` и `VITE_YANDEX_CAPTCHA_SITEKEY`; пока они
  пустые — проверка выключена, работают honeypot и лимиты, код менять при
  добавлении ключей не нужно.
- Лимит тела JSON-запроса 1 МБ; отдельные маршруты загрузки медиа остаются
  со своим лимитом на файл.
- Аудит атак: все ответы 429 и 403 пишутся в `logs/abuse.log`, при 20+
  событиях с одного IP за 5 минут — строка уровня `warn` с пометкой
  «возможная атака».
- Ревизия валидации: пройду по всем маршрутам и добавлю zod-схемы там, где
  `query`/`params` ещё разбираются без схемы (проверка показала, что тела
  запросов и большинство параметров уже под схемами, сырых конкатенаций в
  SQL нет — все значения идут через `$1, $2`).

### Фронтенд

- Общий хук защиты от повторной отправки: кнопка блокируется на 2 секунды
  и до ответа сервера. Подключаю ко всем формам (вход, регистрация,
  онбординг, объявление, поддержка, жалоба, вход в админку).
- Проверка XSS: убеждаюсь, что описания объявлений, сообщения чата, био и
  ответы поддержки выводятся только как текст. `dangerouslySetInnerHTML`
  встречается один раз — во внутреннем файле темы графиков, пользовательских
  данных там нет.

## 4. Отчёт

В конце — конкретный отчёт: изменённые файлы, таблица применённых лимитов по
маршрутам, где стоит капча и honeypot, что именно проверено на XSS и
SQL-инъекции. Отдельно, вне кода, дам команды для Nginx: `limit_req_zone`,
`limit_conn_zone` и блокировку известных плохих User-Agent.

## Технические детали

- Новые зависимости сервера: `otplib` (TOTP), `ioredis` (лимиты),
  `qrcode-terminal` (ASCII-QR в консоли).
- Новые переменные: `TOTP_ENCRYPTION_KEY`, `REDIS_*`, `YANDEX_CAPTCHA_SECRET`,
  `ADMIN_SESSION_TTL` (по умолчанию `2h`), `ABUSE_LOG_FILE`;
  на фронте `VITE_ADMIN_PATH`, `VITE_YANDEX_CAPTCHA_SITEKEY`.
- Админ-токен подписывается отдельным ключом `JWT_ADMIN_SECRET` и содержит
  метку `scope: "admin"`; обычный access-токен админку не открывает, а
  админ-токен не работает на пользовательских маршрутах.
- Все DTO админки остаются без паролей, хешей, кодов и путей к файлам
  верификации.
- Документация: `API.md` (вход в админку, лимиты, капча), `DATABASE.md`
  (миграция 007), `DEPLOY.md` и `SERVER-SETUP.md` (Redis, переменные, Nginx),
  `.env.example` обоих уровней.
- Сквозной тест на локальной базе: вход без TOTP отклоняется, с верным кодом
  проходит, каждый раздел админки открывается, действия пишутся в аудит,
  истёкший админ-токен требует повторного входа.
