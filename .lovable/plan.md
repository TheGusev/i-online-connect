# Незакрытый сценарий: сбой загрузки экрана внутри маршрутизатора

## Что подтверждено по коду

- В `src/router.tsx` у роутера сейчас нет ни `onError`, ни `defaultErrorComponent` — заданы только `routeTree`, `context`, `scrollRestoration`, `defaultPreloadStaleTime: 0`.
- Предзагрузка ссылок не включена (`defaultPreload` не задан), то есть уровень 3 из файла сейчас в приложении не применим; отдельно проверю, что при ручном `router.preloadRoute` защита тоже работает.
- В `src/routes/__root.tsx` у корневого маршрута задан свой `errorComponent`. Он перехватывает ошибки всех вложенных экранов, поэтому `defaultErrorComponent` роутера до них не доходит — значит проверку нужно добавить и в корневой экран ошибки, иначе «сеть безопасности» не сработает.
- Одноразовая защита от повторных перезагрузок уже есть в `src/lib/chunk-recovery.ts` (отметка в памяти сессии + одна перезагрузка + аварийный экран при повторе). Вторую систему отметок не создаю — подключаю ту же самую.

## Что сделаю

1. Из модуля восстановления открываю наружу одну функцию «сбой загрузки кода приложения» — ту же, что уже используется для глобальных ошибок: одна тихая перезагрузка, при повторе фирменный экран «Не удалось загрузить обновление» с кнопкой. Отметка о попытке — одна общая.
2. Подключаю её к обработчику ошибок маршрутизатора: если при переходе на экран не удалось загрузить его код, приложение один раз тихо перезагружается под фирменным экраном загрузки, и человек попадает на нужный экран уже на новой версии.
3. Добавляю тот же разбор в корневой экран ошибки и в экран ошибки по умолчанию: если причина — не загрузился код, вместо надписи об ошибке показывается экран загрузки и идёт перезагрузка; любые другие ошибки по-прежнему показывают обычный экран с кнопками.
4. Глобальный перехват оставляю как есть — он нужен для отдельных подгружаемых частей вне переходов между экранами.
5. Прогоняю именно тот сценарий, который раньше не срабатывал: собираю версию A, открываю экран, подменяю сборку на версию B с другими именами файлов, затем перехожу на другой экран и обратно кликом внутри приложения (без перезагрузки страницы) — ожидаю одну тихую перезагрузку и рабочий экран. Отдельно проверю случай удалённого файла экрана и предзагрузку.

## Технические детали

- `src/lib/chunk-recovery.ts`: экспорт `handleChunkLoadFailure(error: unknown)` — обёртка над существующими `isChunkError` + `recover()` (общий `RELOAD_FLAG`, `keepSplash()`, `registration.update()`, `location.reload()`, `markFatal()` при повторе); плюс экспорт `isChunkLoadError(error)` для проверки в компонентах ошибки.
- `src/router.tsx`: в `createRouter` добавляю `onError: (error) => handleChunkLoadFailure(error)` и `defaultErrorComponent: ({ error }) => isChunkLoadError(error) ? (handleChunkLoadFailure(error), null) : <RouterErrorFallback error={error} />` (побочный вызов выносится в тело функции, не в тернарник).
- `src/routes/__root.tsx`: в существующем `ErrorComponent` первым делом `isChunkLoadError(error)` → `handleChunkLoadFailure(error)` в `useEffect` и `return null` (splash уже виден, экран не мигает); остальная логика без изменений.
- Расширяю распознавание в `CHUNK_ERROR_PATTERNS`: добавляю `"module not found"` и `"dynamically imported module"` без префикса, чтобы попадали и формулировки Safari/iOS.
- Проверки: `bunx tsgo --noEmit`, `bun run build:static`, Playwright-прогон по сценарию «удалённый чанк + клиентская навигация туда-обратно» на локальной раздаче собранной статики, и второй прогон через `router.preloadRoute`.
- Новых пакетов, переменных окружения и миграций не требуется.

Реальный прогон на iPhone с установленным приложением после выкладки версии B остаётся за вами.
