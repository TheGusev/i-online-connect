# Яндекс.Метрика и надёжная видео-верификация

## Подтверждённая диагностика

- Счётчик `112270169` уже добавлен в общий shell приложения: первичный просмотр регистрируется и предусмотрены отдельные `hit` при SPA-переходах. В опубликованной сейчас сборке кода Метрики ещё нет — нужна новая статическая сборка и выкладка.
- Видео отправляется через обычный `fetch` без прогресса и ограничения ожидания. При зависшем соединении кнопка остаётся в состоянии загрузки бесконечно.
- Один POST сейчас последовательно загружает файл, запускает `ffmpeg` три раза и ждёт AI до 60 секунд. Общий Nginx-конфиг из документации обрывает API уже через 30 секунд.
- В кратком Nginx-примере отсутствует лимит 45 МБ, поэтому при его буквальном использовании стандартный лимит Nginx 1 МБ отклоняет обычное мобильное видео.
- Известный опубликованный адрес `/api/health` сейчас возвращает HTML приложения, а не JSON backend. Это не доказывает состояние собственного production-сервера, но означает, что на этом адресе полный сценарий верификации сейчас пройти нельзя.

## Что будет сделано

### 1. Надёжная отправка видео

- Перевести отправку verification-видео на XHR upload-клиент с cookies, bearer-токеном, единичным обновлением истёкшей сессии и повтором запроса.
- Добавить процент загрузки, ограниченное время ожидания, понятные сообщения для 401, 413, сетевого обрыва и тайм-аута.
- Перед отправкой проверять размер и тип записи; имя файла выбирать по фактическому MIME (`.webm` или `.mp4`).
- После неоднозначного сетевого сбоя сначала запрашивать статус заявки: если сервер уже принял видео, не заставлять человека записывать его повторно.

### 2. Убрать тяжёлую сверку из HTTP-запроса

- После проверки задания и сохранения видео сразу создавать заявку `pending` и возвращать её клиенту.
- Нарезку кадров и AI-сверку запускать после ответа; по завершении атомарно обновлять заявку в `verified`, `rejected` или оставлять для ручной проверки.
- Добавить жёсткий тайм-аут каждому процессу `ffmpeg`, очистку процесса и диагностическое серверное логирование без персональных данных и содержимого видео.
- Сохранить ручную очередь как безопасный fallback, если AI-ключ отсутствует, AI недоступен, фото нельзя прочитать или автосверка не уверена.

### 3. Понятный экран результата

- Разделить состояния «загружаем видео» и «проверяем»; показывать реальный процент только во время отправки.
- После принятия заявки сразу переводить экран в `pending`, разрешать уйти со страницы и периодически обновлять статус без блокировки интерфейса.
- При `verified` обновлять данные профиля и бейдж доверия; при `rejected` показывать причину и выдавать новое одноразовое задание для повторной записи.
- Исключить вечный spinner при любом исходе запроса.

### 4. Яндекс.Метрика

- Проверить глобальную инициализацию счётчика `112270169`, защиту от повторного подключения скрипта и SPA-просмотры без двойного первого `hit`.
- Оставить `noscript` fallback и убедиться, что CSP/Nginx разрешают `mc.yandex.ru`, `mc.yandex.com` и `yastatic.net`, не ослабляя остальные правила.
- После статической сборки проверить наличие ID в `dist/static/index.html` и загрузку счётчика в браузере.

### 5. Production-конфигурация и документация

- Согласовать оба Nginx-примера: `client_max_body_size 45m`, достаточные upload/read/send timeouts и разрешения камеры/микрофона только для текущего origin.
- Добавить проверку `ffmpeg`, каталога приватных verification-файлов, AI-конфигурации, миграций и `/api/health` в инструкцию выкладки.
- Отдельно отметить, что `/api/health` обязан возвращать JSON backend, а не SPA-shell; иначе маршрутизация `/api` настроена неверно.

## Проверка готовности

- Frontend typecheck и `build:static`; подтверждение кода Метрики в итоговом HTML.
- Backend typecheck и тесты маршрута верификации.
- Интеграционный сценарий с реальным коротким WebM/MP4: получение задания → multipart upload → немедленный `pending` → автоматическое/ручное завершение → чтение статуса.
- Негативные сценарии: просроченное задание, видео больше лимита, неверный формат, отсутствующее фото, зависший `ffmpeg`, недоступный AI и сетевой обрыв.
- Browser-проверка мобильного экрана: прогресс не зависает, нижняя навигация не перекрывает результат, повторная запись работает. Проверку реальной камеры на устройстве дополнить коротким production-чеклистом, поскольку headless-браузер не заменяет iOS/Android MediaRecorder.
